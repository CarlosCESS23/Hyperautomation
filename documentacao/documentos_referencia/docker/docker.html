01

O que é Docker?

Entendendo o problema que ele resolve

Antes de qualquer comando, precisamos entender o problema real que o Docker resolve. Imagine a seguinte situação:

⚠️
O clássico problema "funciona na minha máquina"

O desenvolvedor roda o projeto localmente sem problemas. Ao enviar para o servidor de produção, tudo quebra. Motivo: versões diferentes de Python, Node, Java, bibliotecas do sistema operacional.

A solução: empacotar tudo junto

Docker resolve isso criando um container — um pacote que inclui a aplicação e todo o ambiente necessário para ela rodar: sistema operacional base, linguagem, dependências, variáveis de ambiente, arquivos de configuração.

📦

Portabilidade

O mesmo container roda identicamente no notebook do dev, no servidor de CI e em produção.

⚡

Leveza

Containers compartilham o kernel do sistema operacional. Iniciam em segundos e consomem MB, não GB.

🔒

Isolamento

Cada container tem seu próprio sistema de arquivos, rede e processos. Não interfere com outros.

🔁

Reprodutibilidade

O ambiente é descrito em código (Dockerfile). Qualquer pessoa cria o mesmo ambiente com um comando.

Container vs. Máquina Virtual

Essa é uma comparação fundamental que todo DevOps precisa dominar:

Aspecto Máquina Virtual (VM) Container Docker
Kernel Próprio (sistema operacional completo) Compartilha o kernel do host
Tamanho Gigabytes (GB) Megabytes (MB)
Inicialização Minutos Segundos (ou menos)
Isolamento Completo (hardware virtualizado) Processo/namespace do SO
Overhead Alto (CPU, RAM, disco) Mínimo
Melhor para Ambientes com SO diferentes, segurança máxima Microsserviços, CI/CD, escala horizontal

Arquitetura do Docker

┌─────────────────────────────────────────────────────────────────┐ │ Seu Computador (Host) │ ├─────────────────────────────────────────────────────────────────┤ │ Docker CLI Docker Daemon (dockerd) Docker Hub │ │ ────────── ──────────────────────── ────────── │ │ docker run ──► Gerencia containers ◄──► images remotas │ │ docker build e imagens locais (cloud) │ │ docker ps │ ├──────────────────────────────────────────────────────────────── │ │ Container A Container B Container C │ │ ─────────── ─────────── ─────────── │ │ App Python App Node.js Banco de dados │ │ + deps + deps PostgreSQL │ ├─────────────────────────────────────────────────────────────────┤ │ Kernel do Sistema Operacional (Linux) │ └─────────────────────────────────────────────────────────────────┘
🧠
Docker Engine = CLI + Daemon + API

Você digita comandos na docker CLI. Ela se comunica com o Docker Daemon via API REST. O Daemon é quem realmente cria e gerencia containers, baixa imagens e configura redes.

03

Conceitos Essenciais

O vocabulário que você precisa dominar

Docker tem um vocabulário próprio. Antes de avançar para comandos, é essencial que esses conceitos estejam internalizados, não apenas memorizados.

Image (Imagem)

Uma imagem é um template somente leitura com todas as instruções para criar um container. Pense nela como a receita de um bolo: define os ingredientes (sistema operacional, dependências, código) e o modo de preparo (comandos de configuração).

🧠
Imagens são construídas em camadas (layers)

Cada instrução no Dockerfile cria uma nova camada. Camadas são imutáveis e reutilizáveis — se duas imagens compartilham a mesma camada base, ela é armazenada apenas uma vez no disco. Isso torna builds e pulls muito mais rápidos.

Anatomia de uma imagem em camadas

app/ (sua aplicação) — Camada de escrita (R/W) Container
COPY . /app — código da aplicação Image layer
RUN pip install -r requirements.txt Image layer
COPY requirements.txt . Image layer
FROM python:3.11-slim — imagem base Base image

Container

Um container é uma instância em execução de uma imagem. A mesma imagem pode gerar dezenas de containers simultâneos e independentes. Containers são efêmeros por natureza — quando você para e remove um container, todas as alterações feitas dentro dele são perdidas (a menos que você use volumes).

AnalogiaDockerDescrição
ReceitaImageTemplate somente leitura com instruções
Bolo prontoContainerInstância em execução da imagem
CozinhaDocker EngineAmbiente que executa os containers
Livro de receitasDocker Hub / RegistryRepositório de imagens
GeladeiraVolumeArmazenamento persistente externo
CondomínioNetworkRede privada entre containers

Volume

Volumes são a solução para a efemeridade dos containers. Eles são gerenciados pelo Docker e existem fora do sistema de arquivos do container. Quando o container é removido, o volume persiste.

🚫
Sem volume — dados perdidos

docker rm container → todos os arquivos criados dentro somem para sempre.

✅
Com volume — dados persistem

docker rm container → volume continua existindo, pronto para o próximo container.

Network (Rede)

Redes Docker permitem que containers se comuniquem entre si por nome — sem precisar conhecer endereços IP que mudam a cada reinício.

🌉

bridge (padrão)

Rede isolada no host. Containers na mesma rede bridge se comunicam. É o padrão ao usar docker network create.

🖥️

host

Container compartilha a rede do host diretamente. Sem isolamento de rede. Melhor performance mas menos seguro.

🔒

none

Sem rede. Container completamente isolado. Usado para processamento offline sem necessidade de rede.

🌐

overlay

Para orquestração (Docker Swarm). Conecta containers em múltiplos hosts físicos. Usado em produção distribuída.

Registry

Um registry é um repositório de imagens Docker. O Docker Hub é o registry público padrão — contém milhares de imagens oficiais. Empresas usam registries privados (AWS ECR, Google Artifact Registry, GitHub Container Registry, Harbor).

Prática 4.1

🧪 Explorando containers interativos

Vamos entender na prática como containers são efêmeros. Execute os comandos abaixo um por vez e observe o comportamento:

bash
# 1. Entrar DENTRO de um container Ubuntu
docker run -it --name lab ubuntu:22.04 bash

# Dentro do container, execute:
ls /
whoami
hostname
cat /etc/os-release
# Instale algo
apt update && apt install -y curl -q
curl https://httpbin.org/get | head -5
# Sair do container
exit

# 2. Tentar entrar novamente e verificar que curl foi perdido
docker start -ai lab
curl --version   # curl ainda está! (container pausado, não removido)
exit

# 3. Remover o container e criar um novo com a MESMA imagem
docker rm lab
docker run -it --name lab2 ubuntu:22.04 bash
curl --version   # ERRO! curl não existe mais — novo container, ambiente limpo
💡
Conclusão desta prática

docker stop para o container mas mantém dados. docker rm apaga o container e tudo dentro. docker run cria um container novo do zero.

Comandos de gerenciamento — referência rápida

bash — ciclo de vida
# ── LISTAR ───────────────────────────────────────────────────────
docker ps               # containers em execução
docker ps -a            # TODOS os containers (incluindo parados)
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

# ── INICIAR / PARAR / REMOVER ─────────────────────────────────────
docker stop NOME_OU_ID  # para graciosamente (SIGTERM → aguarda 10s → SIGKILL)
docker kill NOME_OU_ID  # para imediatamente (SIGKILL)
docker start NOME       # reinicia um container parado
docker restart NOME     # para e reinicia
docker rm NOME          # remove container parado
docker rm -f NOME       # força remoção mesmo rodando

# ── INSPECIONAR ──────────────────────────────────────────────────
docker logs NOME        # ver logs do container
docker logs -f NOME     # acompanhar logs em tempo real (follow)
docker logs --tail 50 NOME  # últimas 50 linhas
docker stats            # monitorar CPU/RAM/rede em tempo real
docker inspect NOME     # todos os detalhes em JSON
docker top NOME         # processos rodando dentro do container

# ── EXECUTAR COMANDOS ─────────────────────────────────────────────
docker exec -it NOME bash  # entrar em container em execução
docker exec NOME ls /app   # executar comando sem entrar
docker cp NOME:/app/log.txt ./log.txt  # copiar arquivo do container

# ── IMAGENS ──────────────────────────────────────────────────────
docker images           # listar imagens locais
docker pull python:3.11-slim  # baixar imagem sem executar
docker rmi python:3.11-slim   # remover imagem local
docker image prune       # remover imagens sem tag ("dangling")

# ── LIMPEZA GERAL ────────────────────────────────────────────────
docker system df         # uso de espaço
docker system prune      # remove containers parados + imagens sem tag + redes não usadas
docker system prune -a   # ⚠️  remove TUDO que não está em uso

Imagens e Dockerfile

Criando suas próprias imagens Docker

O Dockerfile é o DNA da sua imagem. É um arquivo de texto com instruções que o Docker executa, passo a passo, para construir a imagem.

Instruções essenciais do Dockerfile

InstruçãoO que fazExemplo
FROMDefine a imagem base (obrigatório, sempre primeiro)FROM python:3.11-slim
WORKDIRDefine o diretório de trabalho atualWORKDIR /app
COPYCopia arquivos do host para a imagemCOPY . .
ADDComo COPY mas também aceita URLs e .tar.gzADD app.tar.gz /app
RUNExecuta comando durante o build (cria uma camada)RUN pip install -r requirements.txt
ENVDefine variável de ambiente permanenteENV PORT=5000
ARGVariável disponível APENAS durante o buildARG VERSION=1.0
EXPOSEDocumenta a porta que o container usaEXPOSE 5000
VOLUMEDeclara ponto de montagem de volumeVOLUME ["/data"]
USERDefine usuário para execução (nunca root!)USER appuser
HEALTHCHECKComando para verificar saúde do containerHEALTHCHECK CMD curl -f http://localhost/health
CMDComando padrão ao iniciar o container (pode ser substituído)CMD ["python", "app.py"]
ENTRYPOINTPonto de entrada fixo (não substituído pelo docker run)ENTRYPOINT ["gunicorn"]
LABELMetadados da imagemLABEL version="1.0"

Dockerfile simples — aplicação Python Flask

Dockerfile
# ── Imagem base ──────────────────────────────────────────────────
FROM python:3.11-slim

# ── Metadados ────────────────────────────────────────────────────
LABEL maintainer="devops@ax.academy"
LABEL description="API de exemplo"

# ── Diretório de trabalho ─────────────────────────────────────────
WORKDIR /app

# ── Dependências ANTES do código (aproveita cache!) ───────────────
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# ── Código da aplicação ────────────────────────────────────────────
COPY . .

# ── Variáveis de ambiente ─────────────────────────────────────────
ENV FLASK_ENV=production
ENV PORT=5000

# ── Porta exposta ─────────────────────────────────────────────────
EXPOSE 5000

# ── Health check ─────────────────────────────────────────────────
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:5000/health')"

# ── Usuário não-root ─────────────────────────────────────────────
RUN adduser --disabled-password --gecos '' appuser
USER appuser

# ── Comando de inicialização ──────────────────────────────────────
CMD ["python", "app.py"]

Multi-stage build — imagens menores e mais seguras

Multi-stage build é uma técnica avançada mas essencial em produção. Você usa um container "pesado" para compilar/instalar e um container "leve" para rodar. O resultado final é muito menor.

Dockerfile — multi-stage
# ═══ STAGE 1: Builder (instalar dependências) ════════════════════
FROM python:3.11-slim AS builder

WORKDIR /build
COPY requirements.txt .

# Instala no diretório /deps (não no sistema)
RUN pip install --no-cache-dir --target=/build/deps -r requirements.txt

# ═══ STAGE 2: Runtime (imagem final) ═════════════════════════════
FROM python:3.11-slim AS runtime

# Copia APENAS as dependências instaladas pelo builder
COPY --from=builder /build/deps /usr/local/lib/python3.11/site-packages

WORKDIR /app
COPY app/ ./app/
COPY run.py .

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

# Volume para dados persistentes
VOLUME ["/data"]
EXPOSE 5000

# Usuário não-root
RUN adduser --disabled-password --gecos '' appuser && \
    mkdir -p /data && chown appuser:appuser /data
USER appuser

HEALTHCHECK --interval=30s --timeout=10s --start-period=15s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:5000/health')"

CMD ["python", "run.py"]

Construindo e testando a imagem

bash
# Build básico (tag = nome:versão)
docker build -t minha-app:1.0.0 .

# Build com target específico (multi-stage)

Prática 5.1

🧪 Construindo sua primeira imagem

bash — criar app e Dockerfile
# Criar estrutura do projeto
mkdir lab-docker && cd lab-docker

# Criar a aplicação Python
cat > app.py << 'EOF'
from flask import Flask, jsonify
import os, socket, datetime

app = Flask(__name__)

@app.route('/health')
def health():
    return jsonify({
        "status": "ok",
        "hostname": socket.gethostname(),
        "time": datetime.datetime.utcnow().isoformat()
    })

@app.route('/')
def index():
    return jsonify({"message": "Olá do Docker!", "version": "1.0.0"})

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
EOF

# Criar requirements.txt
echo "Flask==3.0.3" > requirements.txt

# Criar Dockerfile
cat > Dockerfile << 'EOF'
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

# Criar .dockerignore
echo -e "__pycache__/\n*.pyc\n.env" > .dockerignore

# Construir a imagem
docker build -t lab-app:1.0.0 .

# Executar
docker run -d --name lab-app -p 5000:5000 lab-app:1.0.0

# Testar
curl http://localhost:5000/health
curl http://localhost:5000/

Volumes e Redes

Persistência de dados e comunicação entre containers

Tipos de volume no Docker

📁

Named Volume

Gerenciado pelo Docker. Persiste após docker rm. Recomendado para dados de produção (bancos, arquivos da aplicação).

🔗

Bind Mount

Mapeia um diretório do seu computador. Ideal para desenvolvimento: altera o código e o container vê na hora, sem rebuild.

⚡

tmpfs Mount

Armazenamento em memória RAM. Rápido mas não persiste. Usado para dados temporários sensíveis (senhas em memória).

bash — gerenciamento de volumes
# ── Named Volumes ─────────────────────────────────────────────────
docker volume create meus-dados
docker volume ls
docker volume inspect meus-dados
# Mostra onde o volume está no disco do host

# Usar volume em container
docker run -d --name db \
  -v meus-dados:/var/lib/postgresql/data \
  postgres:16-alpine

# ── Bind Mount ────────────────────────────────────────────────────
# Mapeia pasta local para desenvolvimento (hot reload)
docker run -d --name dev-app \
  -v $(pwd)/src:/app/src \
  -p 5000:5000 \
  minha-app:dev
# Altere arquivos em ./src e veja a mudança no container!

# ── Demonstração de persistência ──────────────────────────────────
docker volume create demo-vol
docker run --rm -v demo-vol:/dados ubuntu bash -c "echo 'dados importantes' > /dados/arquivo.txt"
docker run --rm -v demo-vol:/dados ubuntu cat /dados/arquivo.txt
# "dados importantes" — persiste mesmo sem o container!

# Remover volume (só após remover containers que o usam)
docker volume rm demo-vol
docker volume prune  # remove volumes não usados por nenhum container

Redes Docker na prática

bash — gerenciamento de redes
# ── Criar rede ────────────────────────────────────────────────────
docker network create app-network
docker network ls
docker network inspect app-network

# ── Conectar containers na mesma rede ─────────────────────────────
# Container 1: banco de dados
docker run -d \
  --name postgres \
  --network app-network \
  -e POSTGRES_PASSWORD=senha123 \
  -e POSTGRES_DB=meubanco \
  postgres:16-alpine

# Container 2: aplicação que conecta ao banco pelo NOME
docker run -d \
  --name api \
  --network app-network \
  -e DATABASE_URL=postgresql://postgres:senha123@postgres:5432/meubanco \
  -p 5000:5000 \
  minha-app:1.0.0

# A API acessa o banco pelo hostname "postgres" — não por IP!
# Docker resolve o nome automaticamente dentro da rede

# Verificar conectividade entre containers
docker exec -it api ping postgres
docker exec -it api nslookup postgres

# Conectar container existente a uma nova rede
docker network connect app-network outro-container
Prática 6.1

🧪 Persistência comprovada na prática

bash
# Criar volume para o banco Jenkins
docker volume create jenkins-data

# Subir Jenkins com volume
docker run -d \
  --name jenkins \
  --restart unless-stopped \
  -p 8080:8080 \
  -v jenkins-data:/var/jenkins_home \
  jenkins/jenkins:lts-jdk17

# Aguardar inicialização e pegar senha
docker logs -f jenkins 2>&1 | grep -A2 "initialAdminPassword"

# Acessar http://localhost:8080 e configurar Jenkins
# Crie um job de teste...

# REMOVER o container (simular falha de servidor)
docker rm -f jenkins

# Recriar com o MESMO volume
docker run -d \
  --name jenkins \
  --restart unless-stopped \
  -p 8080:8080 \
  -v jenkins-data:/var/jenkins_home \
  jenkins/jenkins:lts-jdk17

# Acessar http://localhost:8080 — o job criado ainda existe!
# Essa é a magia dos volumes: o container sumiu, os dados ficaram.

Docker Compose

Orquestrando múltiplos containers como uma aplicação única

O Docker Compose resolve um problema real: aplicações modernas raramente são um único container. Uma aplicação típica tem API, banco de dados, cache (Redis), fila de mensagens (RabbitMQ)... Gerenciar isso com docker run separados é caótico.

Com o Compose, você descreve toda a infraestrutura em um único arquivo YAML e sobe tudo com um comando.

Anatomia do docker-compose.yml

docker-compose.yml — comentado
version: '3.9'   # versão do formato Compose

services:           # cada serviço = um container

  api:               # nome do serviço (usado como hostname na rede interna)
    build:
      context: .         # pasta com o Dockerfile
      target: runtime   # stage do multi-stage build
    container_name: minha-api
    restart: unless-stopped
    ports:
      - "5000:5000"
    environment:               # variáveis de ambiente
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
      - REDIS_URL=redis://cache:6379
      - DEBUG=false
    env_file:                  # ou carregar de arquivo .env
      - .env
    volumes:
      - app-data:/data
    depends_on:                # aguarda esses serviços iniciarem
      db:
        condition: service_healthy  # espera o healthcheck passar
    networks:
      - app-net
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 30s
      timeout: 10s
      retries: 3

Docker Hub e Registry

Publicando e distribuindo suas imagens

O que é um Registry?

Um registry é um servidor que armazena e distribui imagens Docker. O Docker Hub é o registry público padrão. Para imagens privadas ou corporativas, existem alternativas como AWS ECR, Google Artifact Registry e GitHub Container Registry.

bash — Docker Hub
# ── Autenticação ──────────────────────────────────────────────────
docker login                         # login no Docker Hub
docker login ghcr.io                 # GitHub Container Registry
docker logout

# ── Publicar imagem ───────────────────────────────────────────────
# Padrão de nomenclatura: USUARIO/REPOSITORIO:TAG
docker tag lab-app:1.0.0 meuusuario/lab-app:1.0.0
docker tag lab-app:1.0.0 meuusuario/lab-app:latest

docker push meuusuario/lab-app:1.0.0
docker push meuusuario/lab-app:latest

# ── Baixar imagem ─────────────────────────────────────────────────
docker pull meuusuario/lab-app:1.0.0

# ── Boas práticas de tagging ──────────────────────────────────────
docker tag lab-app:1.0.0 meuusuario/lab-app:1.0.0    # versão semântica
docker tag lab-app:1.0.0 meuusuario/lab-app:sha-a3f8b2c  # hash do commit
docker tag lab-app:1.0.0 meuusuario/lab-app:latest    # última versão
# NUNCA use só :latest em produção — você perde rastreabilidade!
🔐
Use Access Tokens, não sua senha

Em pipelines CI/CD, nunca use sua senha do Docker Hub diretamente. Crie um Access Token em hub.docker.com → Account Settings → Security. Tokens têm escopos limitados e podem ser revogados individualmente.

Docker no CI/CD

Integrando Docker com GitHub Actions e Jenkins

GitHub Actions — build e push automático

.github/workflows/docker.yml
name: Build e Push Docker

on:
  push:
    branches: [ main ]
    tags: [ 'v*.*.*' ]

jobs:
  docker:
    runs-on: ubuntu-latest
    steps:
      # 1. Checkout do código
      - uses: actions/checkout@v4

      # 2. Configurar Docker Buildx (builds multi-arch)
      - uses: docker/setup-buildx-action@v3

      # 3. Login no Docker Hub
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      # 4. Extrair metadados (tags automáticas)
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ${{ secrets.DOCKERHUB_USERNAME }}/minha-app
          tags: |
            type=sha,prefix=sha-
            type=semver,pattern={{version}}
            type=raw,value=latest,enable={{is_default_branch}}

      # 5. Build e Push com cache
      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha       # cache do GitHub Actions
          cache-to: type=gha,mode=max

      # 6. Testar a imagem publicada
      - name: Testar health check
        run: |
          docker run -d --name test-container -p 5000:5000 \
            ${{ secrets.DOCKERHUB_USERNAME }}/minha-app:latest
          sleep 10
          curl -f http://localhost:5000/health || exit 1
          docker rm -f test-container

Jenkinsfile — pipeline com Docker agent

Jenkinsfile
pipeline {
    agent any

    environment {
        IMAGE_NAME  = "meuusuario/minha-app"
        IMAGE_TAG   = "sha-${env.GIT_COMMIT.take(7)}"
        DOCKER_CRED = credentials('dockerhub-token')
    }

    stages {
        stage('Testes em Container Python') {
            // Os testes rodam em container limpo — zero poluição no agente
            agent { docker { image 'python:3.11-slim' } }
            steps {
                sh 'pip install -r requirements-dev.txt -q'
                sh 'pytest tests/ -v --cov=app'
            }
        }

        stage('Build da Imagem') {
            steps {
                script {
                    docker.build("${IMAGE_NAME}:${IMAGE_TAG}")
                }
            }
        }

        stage('Push para Registry') {
            steps {
                script {
                    docker.withRegistry('https://index.docker.io/v1/', 'dockerhub-token') {
                        docker.image("${IMAGE_NAME}:${IMAGE_TAG}").push()
                        docker.image("${IMAGE_NAME}:${IMAGE_TAG}").push('latest')
                    }
                }
            }
        }

        stage('Deploy Blue-Green') {
            steps {
                sh """
                    docker run -d \\
                      --name app-green \\
                      -p 5001:5000 \\
                      -v app-data:/data \\
                      ${IMAGE_NAME}:${IMAGE_TAG}
                    sleep 8
                    curl -sf http://localhost:5001/health || exit 1
                    docker rm -f app-blue 2>/dev/null || true
                    docker rename app-green app-blue
                """
            }
        }
    }

    post {
        failure { sh 'docker rm -f app-green 2>/dev/null || true' }
    }
}

Boas Práticas

O que separa um container amador de um container production-ready

✅ Faça isso

✅
Use imagens base mínimas

python:3.11-slim em vez de python:3.11. Reduz superfície de ataque e tamanho da imagem em 70%.

✅
Copie requirements.txt ANTES do código

Se só o código mudou, o Docker usa o cache da camada de dependências. Build muito mais rápido.

✅
Execute como usuário não-root

USER appuser no Dockerfile. Se o container for comprometido, o atacante não tem privilégios de root no host.

✅
Adicione HEALTHCHECK

Docker e orquestradores (Kubernetes, Swarm) usam o healthcheck para saber se o container está realmente saudável, não apenas "rodando".

✅
Use .dockerignore sempre

Evita incluir node_modules, .git, arquivos de teste e variáveis de ambiente na imagem.

🚫 Nunca faça isso

🚫
Credenciais no Dockerfile ou imagem

Nunca ENV DB_PASSWORD=senha no Dockerfile. Use variáveis de ambiente em runtime ou Docker Secrets.

🚫
Tag :latest em produção

Se você fizer rollback de :latest, qual versão você está rodando? Use sempre tags semânticas ou de commit SHA.

🚫
Múltiplos processos em um container

Um container = um processo principal. Não rode Nginx + Python + cron no mesmo container. Use Compose para isso.

🚫
Dados importantes sem volume

docker rm apaga tudo dentro do container. Banco de dados, uploads, logs — sempre em volumes nomeados.

🚫
Rodar como root (USER root)

É o padrão se você não especificar USER. Em produção, crie sempre um usuário sem privilégios.

Otimização de camadas — exemplo concreto

❌ Ruim — muitas camadas
RUN apt update
RUN apt install -y git
RUN apt install -y curl
RUN apt clean
RUN rm -rf /var/lib/apt/lists/*
# 5 camadas desnecessárias!
✅ Bom — camada única
RUN apt update && \
    apt install -y git curl && \
    apt clean && \
    rm -rf /var/lib/apt/lists/*
# 1 camada — mais limpo e menor!

FROM python:3.11-slim AS runtime
LABEL maintainer="turma-devops"

WORKDIR /app
COPY app/ ./app/

EXPOSE 5000

RUN adduser --disabled-password --gecos '' appuser && \
    mkdir -p /data && chown appuser:appuser /data
USER appuser

HEALTHCHECK --interval=30s --timeout=10s --start-period=15s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:5000/health')"

CMD ["python", "run.py"]

Desafios

Pratique e consolide o aprendizado

🟢 Nível Fácil

Desafio 1 — Container com variáveis de ambiente

  • Rode um container Nginx com uma variável APP_ENV=producao
  • Use docker exec para verificar que a variável existe dentro do container
  • Salve as variáveis em um arquivo .env e use --env-file

Desafio 2 — Persistência com Named Volume

  • Crie um volume chamado meu-volume
  • Rode um container Ubuntu, crie um arquivo com seu nome dentro do volume
  • Remova o container e crie um novo — confirme que o arquivo ainda existe
  • Use docker volume inspect para descobrir onde o arquivo está no disco

Desafio 3 — Dockerfile básico

  • Crie uma aplicação Python simples que exibe "Olá do Docker! — [SEU NOME]"
  • Escreva um Dockerfile com FROM, WORKDIR, COPY, RUN e CMD
  • Faça o build e rode o container
  • Verifique o histórico de camadas com docker history

🟡 Nível Médio

Desafio 4 — Stack com Docker Compose

  • Crie um docker-compose.yml com: API Python Flask + PostgreSQL + Redis
  • Configure o serviço de banco com healthcheck (pg_isready)
  • Faça a API depender do banco usando depends_on: condition: service_healthy
  • Suba tudo com um comando e demonstre que os 3 serviços se comunicam

Desafio 5 — Comparando tamanhos de imagem

  • Crie 3 versões do mesmo Dockerfile: usando python:3.11, python:3.11-slim e multi-stage
  • Compare os tamanhos com docker images
  • Documente a diferença de tamanho em um README.md

🔴 Nível Difícil

Desafio 6 — Monitoramento com Prometheus + Grafana

  • Adicione flask-prometheus-metrics à AgendaFácil e exponha /metrics
  • Adicione containers do Prometheus e Grafana no docker-compose.yml
  • Configure o Prometheus para coletar métricas da API
  • Crie um dashboard Grafana com: requisições por segundo, latência e erros
  • Bônus: configure alertas quando a taxa de erro for maior que 5%

Desafio 7 — Deploy Blue-Green completo

  • Crie 2 versões da sua API: v1 retorna {"version":"1.0"} e v2 retorna {"version":"2.0"}
  • Implemente um script deploy.sh que: sobe v2, faz healthcheck, direciona tráfego, remove v1
  • Adicione rollback automático se o healthcheck de v2 falhar
  • Integre o script em um Jenkinsfile como stage de Deploy
