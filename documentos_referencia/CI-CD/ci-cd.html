O que é Git?

O sistema de controle de versão mais usado no mundo

Git é um sistema de controle de versão distribuído criado por Linus Torvalds em 2005 para gerenciar o desenvolvimento do kernel Linux. Hoje é usado por praticamente todos os projetos de software no mundo.

🧠
Problema que o Git resolve

Sem controle de versão: "projeto_final_v3_agora_vai_MESMO.zip". Com Git: histórico completo, quem mudou o quê, quando e por quê — e a capacidade de voltar a qualquer ponto.

Arquitetura distribuída

Diferente de sistemas centralizados (SVN, CVS), no Git cada desenvolvedor tem uma cópia completa do repositório — histórico incluído. Não há ponto único de falha.

Git é distribuído: cada desenvolvedor tem uma cópia completa e pode trabalhar offline

Os 3 estados de um arquivo no Git

O fluxo obrigatório: editar → git add → git commit

Por que todo desenvolvedor precisa de Git?

📜

Histórico auditável

Cada alteração tem autor, data e mensagem explicando o porquê. Git blame mostra quem escreveu cada linha.

🔀

Trabalho em paralelo

Branches permitem desenvolver features simultaneamente sem conflitar com outros devs.

🔙

Rollback instantâneo

Quebrou produção? git revert ou git reset restaura qualquer versão anterior em segundos.

🔗

Base do CI/CD

GitHub Actions, Jenkins, GitLab CI — todos dependem de eventos Git (push, PR, tag) para disparar pipelines.

Repositório e Commits

Criando e versionando seu primeiro projeto

Criando um repositório

bash
# ── Inicializar um repositório novo ──────────────────────────────
mkdir meu-projeto && cd meu-projeto
git init
# Cria a pasta oculta .git — o coração do repositório
ls -la

# ── Clonar um repositório existente ─────────────────────────────
git clone https://github.com/usuario/repositorio.git
git clone https://github.com/usuario/repositorio.git minha-pasta
# Clona em pasta com nome específico

O ciclo completo: editar → add → commit

bash — ciclo de trabalho
# ── 1. Ver o estado atual dos arquivos ───────────────────────────
git status
# Use git status SEMPRE — é seu GPS dentro do Git

# ── 2. Ver as diferenças antes de adicionar ──────────────────────
git diff              # mudanças no working directory
git diff --staged     # mudanças na staging area (pós git add)

# ── 3. Adicionar ao staging ───────────────────────────────────────
git add arquivo.py    # arquivo específico
git add src/           # todos os arquivos de uma pasta
git add .              # tudo no diretório atual
git add -p             # modo interativo — escolhe trecho por trecho

# ── 4. Commitar ────────────────────────────────────────────────────
git commit -m "feat: adiciona endpoint de login"
git commit -am "fix: corrige validação de email"
# -am = add + commit (só arquivos já rastreados)

# ── 5. Ver histórico ──────────────────────────────────────────────
git log                              # completo
git log --oneline                    # compacto
git log --oneline --graph --all      # com grafo de branches
git log --oneline -10                # últimos 10
git log --author="Emmerson"          # por autor
git log --since="2025-01-01"         # por data
git log -S "função_buscada"          # busca no conteúdo

💡
Regra de ouro para mensagens de commit

Complete a frase: "Se aplicado, este commit vai ___". Exemplo: "adicionar endpoint de login" → feat: adiciona endpoint de login. Mensagem no imperativo, sem ponto final, máximo 72 caracteres.

Desfazendo alterações

bash — cenários de desfazer
# ── Cenário 1: arquivo modificado, não adicionado ────────────────
git restore arquivo.py          # descarta mudanças (irreversível!)
git checkout -- arquivo.py      # equivalente (sintaxe antiga)

# ── Cenário 2: arquivo no staging (git add foi feito) ────────────
git restore --staged arquivo.py # remove do staging, mantém mudanças
git reset HEAD arquivo.py       # equivalente (sintaxe antiga)

# ── Cenário 3: desfazer o ÚLTIMO commit, manter mudanças ─────────
git reset --soft HEAD~1         # volta ao staging
git reset --mixed HEAD~1        # volta ao working dir (padrão)

# ── Cenário 4: desfazer commit E descartar mudanças ──────────────
git reset --hard HEAD~1         # ⚠️  DESTRUTIVO — mudanças perdidas
# NUNCA use --hard em commits já enviados ao remoto compartilhado

# ── Cenário 5: desfazer de forma SEGURA (recomendado em equipes) ─
git revert HEAD                 # cria novo commit que desfaz o último
git revert a3f8b2c              # reverte um commit específico pelo hash
# revert preserva o histórico — ideal para branches compartilhadas

# ── Ver quem escreveu cada linha ─────────────────────────────────
git blame src/app.py            # linha por linha: hash, autor, data
git blame -L 10,25 src/app.py  # apenas linhas 10-25

Branches e Merge

Trabalhando em paralelo sem conflitar

Uma branch é uma linha independente de desenvolvimento. Criar branches no Git é instantâneo e tem custo zero — são apenas ponteiros para commits.

Branches permitem trabalho paralelo — hotfix e feature evoluem independentemente e são integradas na main via merge

Comandos de branch

bash — branches
# ── Criar e navegar ──────────────────────────────────────────────
git branch                       # listar branches (* = atual)
git branch -a                    # incluindo remotas
git switch -c feature/login      # criar e entrar (modo moderno)
git checkout -b feature/login    # equivalente (modo clássico)
git switch main                  # trocar de branch
git branch -d feature/login      # deletar branch (após merge)
git branch -D feature/login      # forçar delete (sem merge)
git branch -m novo-nome          # renomear a branch atual

# ── Merge ────────────────────────────────────────────────────────
git switch main                  # entrar na branch de destino
git merge feature/login          # fast-forward ou three-way merge
git merge --no-ff feature/login  # forçar merge commit (preserva histórico)
git merge --squash feature/login # combina todos os commits em um
git merge --abort                # abortar merge em andamento

Fast-Forward vs Three-Way Merge

Fast-forward: simples e linear. Three-way: necessário quando ambas as branches evoluíram

Prática 4.1

🧪 Fluxo completo de Feature Branch

bash
# Criar a feature branch
git switch -c feature/calculadora

# Trabalhar na feature (2 commits)
echo 'def subtrair(a,b): return a - b' >> calc.py
git add calc.py && git commit -m "feat: adiciona subtração"

echo 'def multiplicar(a,b): return a * b' >> calc.py
git add calc.py && git commit -m "feat: adiciona multiplicação"

# Ver histórico com grafo
git log --oneline --graph --all

# Voltar para main e fazer o merge
git switch main
git merge feature/calculadora

# Deletar a branch após o merge (boa prática)
git branch -d feature/calculadora

git log --oneline --graph --all

Rebase e Conflitos

Histórico linear e resolvendo divergências

Merge vs Rebase — comparação visual

Use merge para branches compartilhadas (main, develop). Use rebase para branches pessoais antes de abrir PR

bash — rebase
# ── Rebase básico ────────────────────────────────────────────────
git switch feature/login
git rebase main          # reaplica commits da feature em cima da main

# ── Rebase interativo — reescrever os últimos 3 commits ──────────
git rebase -i HEAD~3

# No editor, use os comandos:
# pick   → manter o commit como está
# reword → manter o commit, editar a mensagem
# squash → combinar com o commit anterior
# fixup  → combinar com o anterior, descartar esta mensagem
# drop   → descartar o commit completamente

# ── Abortar um rebase em andamento ───────────────────────────────
git rebase --abort

# ── Continuar após resolver conflito de rebase ────────────────────
git add arquivo-resolvido.py
git rebase --continue

Resolvendo Conflitos — passo a passo

Conflito não é erro — é o Git pedindo sua decisão quando duas branches alteram a mesma linha

arquivo com conflito — o que aparece
<<<<<<< HEAD
titulo = "App v1.0 — Versão Estável"     ← SUA versão (branch atual)
=======
titulo = "App v2.0 — Nova Identidade"     ← versão do merge/rebase
>>>>>>> feature/rebrand

# RESOLVER: apagar os marcadores e deixar APENAS o que você quer:
titulo = "App v2.0 — Nova Identidade"     ← decisão tomada

# Finalizar:
git add arquivo_resolvido.py
git commit -m "merge: resolve conflito de título — mantém v2.0"

Stash, Tags e Log

Ferramentas do dia a dia para situações específicas

Git Stash — guardar trabalho temporariamente

bash — stash
# Cenário: você está no meio de algo e precisa trocar de branch urgente
# Mas não quer commitar código incompleto

git stash                                  # salva e limpa o working dir
git stash push -m "WIP: tela de login"     # com mensagem descritiva
git stash push --include-untracked         # inclui arquivos novos

git stash list                             # ver todos os stashes
git stash show stash@{0}                   # ver o que está no stash

git stash pop                              # restaura e remove da lista
git stash apply                            # restaura mas mantém na lista
git stash apply stash@{1}                  # restaurar stash específico

git stash drop stash@{0}                   # remover sem aplicar
git stash clear                            # limpar todos os stashes

# Criar branch a partir de um stash
git stash branch feature/nova-branch stash@{0}

Git Tags — marcando versões

bash — tags e versionamento semântico
# ── Criar tags ────────────────────────────────────────────────────
git tag v1.0.0                              # tag leve (só um marcador)
git tag -a v1.0.0 -m "Release: v1.0.0 — versão inicial estável"
# -a = annotated tag (recomendada): inclui autor, data e mensagem

# Tag em um commit específico
git tag -a v0.9.0 a3f8b2c -m "Release: v0.9.0 beta"

# ── Listar e inspecionar ──────────────────────────────────────────
git tag                                     # listar todas
git tag -l "v1.*"                           # filtrar por padrão
git show v1.0.0                             # detalhes da tag

# ── Enviar para o remoto ──────────────────────────────────────────
git push origin v1.0.0                      # uma tag específica
git push origin --tags                      # todas as tags

# ── Versionamento semântico (MAJOR.MINOR.PATCH) ───────────────────
# v1.0.0  → versão inicial
# v1.0.1  → bugfix
# v1.1.0  → nova feature sem breaking change
# v2.0.0  → breaking change (API incompatível)

Git Log avançado — encontrando qualquer coisa

bash — git log avançado
git log --oneline --graph --all --decorate  # visão completa com grafo
git log -p                                  # com diff de cada commit
git log --stat                              # arquivos alterados por commit
git log --author="Emmerson"
git log --since="2025-01-01" --until="2025-06-01"
git log --grep="login"                      # busca na mensagem
git log -S "nome_da_funcao"                 # busca no conteúdo do código
git log main..feature/login                # commits exclusivos da feature
git log --no-merges                         # sem commits de merge

# Formato personalizado
git log --format="%h  %an  %ar  %s"
#                   ↑    ↑    ↑    ↑
#                 hash autor data  assunto

GitHub e Repositório Remoto

Colaboração na nuvem

🧠
Git ≠ GitHub

Git é a ferramenta local de controle de versão. GitHub é a plataforma web que hospeda repositórios Git na nuvem. Analogia: Git é o Word, GitHub é o Google Drive.

GitHub é o ponto de encontro — cada dev trabalha localmente e sincroniza via push/pull

Conectando local ao remoto

bash — remote, push, pull, fetch
# ── Conectar ao remoto ────────────────────────────────────────────
git remote add origin https://github.com/usuario/repo.git
git remote -v                              # ver remotos configurados
git remote set-url origin URL_NOVA         # trocar URL
git remote remove origin

# ── Primeiro push ─────────────────────────────────────────────────
git push -u origin main
# -u = --set-upstream: vincula branch local com a remota
# após isso, basta: git push

# ── Enviar uma branch nova ────────────────────────────────────────
git push origin feature/login

# ── Baixar atualizações ────────────────────────────────────────────
git fetch origin                           # busca sem integrar
git pull origin main                       # fetch + merge
git pull --rebase origin main              # fetch + rebase (histórico mais limpo)

# ── Clonar e trabalhar ────────────────────────────────────────────
git clone https://github.com/usuario/repo.git
git clone --depth 1 URL                   # clone superficial (apenas último commit)

# ── Deletar branch remota ─────────────────────────────────────────
git push origin --delete feature/login

Gitflow e Estratégias de Branch

Organizando o desenvolvimento em equipe

Gitflow: main (produção), develop (integração), feature (novas funções), release (estabilização) e hotfix (correções urgentes)

BranchOrigemMerge paraQuando usar
main——Código em produção. Apenas merges de release e hotfix
developmainreleaseIntegração contínua — todas as features se encontram aqui
feature/*developdevelopCada nova funcionalidade em branch isolada
release/*developmain + developPreparação de versão: testes, bugfixes menores, bump de versão
hotfix/*mainmain + developCorreção urgente diretamente em produção
ℹ️
Alternativa mais simples: GitHub Flow

Para equipes menores ou projetos com deploy contínuo: apenas main + feature/*. Cada branch vai direto para a main via PR. Mais simples que Gitflow, amplamente usado em startups e projetos open source.

O que é GitHub Actions?

CI/CD nativo integrado ao GitHub

GitHub Actions é a plataforma de CI/CD integrada ao GitHub. Permite automatizar workflows diretamente no repositório, sem servidor externo. Cada push, PR, tag ou evento manual pode disparar uma sequência de ações.

GitHub Actions: evento dispara workflow → jobs rodam em runners paralelos → resultados visíveis no GitHub

Diferença entre GitHub Actions e Jenkins

CritérioGitHub ActionsJenkins
HospedagemGitHub (sem servidor próprio)Servidor próprio ou cloud
ConfiguraçãoYAML no repositório — zero setupUI + Jenkinsfile — requer instalação
CustoGrátis (públicos ilimitado; privado 2.000 min/mês)Open source, paga infraestrutura
Ecosistema20.000+ Actions no Marketplace1.800+ plugins
Integração GitHubNativa — PR checks, badges, statusVia plugins e webhooks
FlexibilidadeLimitada ao que GitHub ofereceTotal — qualquer infra, qualquer SO
Melhor paraProjetos GitHub, equipes ágeis, open sourceEnterprise, pipelines complexos, legado

Workflow YAML

Anatomia completa do arquivo de automação

.github/workflows/ci.yml — estrutura completa comentada
# Nome do workflow (aparece na aba Actions)
name: CI — Integração Contínua

# ── GATILHOS: quando este workflow executa ────────────────────────
on:
  push:
    branches: [ main, develop ]       # push nas branches
    paths:                             # só se esses arquivos mudarem
      - 'src/**'
      - 'tests/**'
      - 'requirements*.txt'
  pull_request:
    branches: [ main ]
    types: [ opened, synchronize, reopened ]
  workflow_dispatch:                   # permite execução manual
    inputs:
      ambiente:
        description: 'Ambiente alvo'
        required: true
        default: 'staging'
        type: choice
        options: [ staging, producao ]
  schedule:
    - cron: '0 8 * * 1-5'             # 8h toda segunda-sexta

# ── VARIÁVEIS globais ─────────────────────────────────────────────
env:
  PYTHON_VERSION: '3.11'
  NODE_VERSION:   '20'
  IMAGE_NAME:     minha-app

# ── JOBS: unidades de trabalho paralelas ──────────────────────────
jobs:

  lint:                                # ID do job (sem espaços)
    name: 🔍 Lint e Qualidade          # nome exibido na UI
    runs-on: ubuntu-latest             # runner (ubuntu/windows/macos)

    steps:
      - uses: actions/checkout@v4      # clonar o repositório

      - uses: actions/setup-python@v5  # configurar Python
        with:
          python-version: ${{ env.PYTHON_VERSION }}
          cache: 'pip'                   # cache das dependências

      - name: Instalar flake8
        run: pip install flake8

      - name: Verificar qualidade
        run: flake8 src/ --max-line-length=100

  testes:
    name: 🧪 Testes Python ${{ matrix.python-version }}
    runs-on: ubuntu-latest
    needs: lint                          # só executa se lint passar

    strategy:
      matrix:
        python-version: [ '3.10', '3.11', '3.12' ]
      fail-fast: false                   # continua mesmo se uma versão falhar

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: 'pip'

      - name: Instalar dependências
        run: pip install -r requirements-dev.txt

      - name: Executar testes com cobertura
        run: pytest tests/ -v --cov=src --cov-report=xml --cov-fail-under=80

      - name: Salvar relatório de cobertura
        uses: actions/upload-artifact@v4
        if: always()                     # salvar mesmo em falha
        with:

CI Pipeline Completo

Lint + testes + cobertura + análise de segurança + Docker

.github/workflows/ci.yml — pipeline profissional completo
name: CI — AgendaFácil

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

env:
  PYTHON_VERSION: '3.11'
  IMAGE:         agendafacil

jobs:

  # ── JOB 1: Qualidade de código ───────────────────────────────────
  qualidade:
    name: 🔍 Lint e Qualidade
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11', cache: pip }
      - run: pip install flake8 black isort
      - name: flake8
        run: flake8 app/ tests/ --max-line-length=100 --ignore=E501,W503
      - name: black (verificar formatação)
        run: black --check app/ tests/
      - name: isort (verificar imports)
        run: isort --check-only app/ tests/

  # ── JOB 2: Testes em matriz ──────────────────────────────────────
  testes:
    name: 🧪 Testes Python ${{ matrix.python-version }}
    runs-on: ubuntu-latest
    needs: qualidade
    strategy:
      matrix:
        python-version: [ '3.10', '3.11', '3.12' ]
      fail-fast: false
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - name: Instalar dependências
        run: pip install -r requirements-dev.txt
      - name: Testes com cobertura
        run: pytest tests/ -v --cov=app --cov-report=xml --cov-fail-under=80
      - name: Subir cobertura como artefato
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: cov-${{ matrix.python-version }}
          path: coverage.xml

  # ── JOB 3: Segurança ─────────────────────────────────────────────
  seguranca:
    name: 🛡️ Análise de Segurança
    runs-on: ubuntu-latest
    needs: qualidade
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11', cache: pip }
      - run: pip install bandit safety
      - name: bandit (vulnerabilidades no código)
        run: bandit -r app/ -ll
      - name: safety (vulnerabilidades em dependências)
        run: safety check -r requirements.txt

  # ── JOB 4: Build Docker (só na main) ─────────────────────────────
  docker:
    name: 🐳 Build e Push Docker
    runs-on: ubuntu-latest
    needs: [ testes, seguranca ]
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ${{ secrets.DOCKERHUB_USERNAME }}/${{ env.IMAGE }}
          tags: |
            type=sha,prefix=sha-
            type=raw,value=latest

      - uses: docker/build-push-action@v5
        with:
          context:    .
          push:       true
          tags:       ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to:   type=gha,mode=max

      - name: Testar imagem publicada
        run: |
          docker run -d --name test -p 5000:5000 \
            ${{ secrets.DOCKERHUB_USERNAME }}/${{ env.IMAGE }}:latest
          sleep 10
          curl -sf http://localhost:5000/health || (docker logs test && exit 1)
          docker rm -f test

name: Release — Build e Publicação

on:
  push:
    tags: [ 'v*.*.*' ]       # dispara ao criar tag v1.0.0

jobs:
  release:
    name: 🏷️ Criar Release e Publicar Imagem
    runs-on: ubuntu-latest
    permissions:
      contents: write         # para criar a release no GitHub

    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0       # fetch completo (para changelog)

      - uses: actions/setup-python@v5
        with: { python-version: '3.11', cache: pip }
      - run: pip install -r requirements-dev.txt && pytest tests/ -v

      # Extrair número da versão da tag
      - name: Extrair versão
        id: version
        run: echo "VERSION=${GITHUB_REF#refs/tags/}" >> $GITHUB_OUTPUT

      # Gerar changelog automático
      - name: Gerar Changelog
        run: |
          PREV_TAG=$(git describe --tags --abbrev=0 HEAD~1 2>/dev/null || echo "")
          if [ -n "$PREV_TAG" ]; then
            git log ${PREV_TAG}..HEAD --oneline --no-merges > CHANGELOG.md
          else
            git log --oneline --no-merges > CHANGELOG.md
          fi
          cat CHANGELOG.md

      # Build e push da imagem com versão semântica
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - uses: docker/build-push-action@v5
        with:
          push:    true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/agendafacil:${{ steps.version.outputs.VERSION }}
            ${{ secrets.DOCKERHUB_USERNAME }}/agendafacil:latest

      # Criar Release no GitHub com changelog
      - uses: softprops/action-gh-release@v1
        with:
          tag_name:   ${{ steps.version.outputs.VERSION }}
          name:       Release ${{ steps.version.outputs.VERSION }}
          body_path:  CHANGELOG.md
          draft:      false
          prerelease: ${{ contains(steps.version.outputs.VERSION, '-') }}

name: Deploy via SSH

Git e GitHub Actions de forma profissional

✅ Git — faça sempre

✅
Commits pequenos e frequentes

Cada commit deve ter um único propósito claro. Mais fácil de revisar, reverter e entender.

✅
Conventional Commits

feat:, fix:, ci:... Padroniza mensagens, facilita CHANGELOG automático.

✅
.gitignore antes do primeiro commit

Criar o .gitignore antes de adicionar arquivos evita commitar lixo acidentalmente.

✅
Feature branches sempre

Nunca commitar direto na main. Toda mudança via branch + PR, mesmo que pequena.

🚫 Git — nunca faça

🚫
git reset --hard em branches compartilhadas

Reescreve histórico e quebra o repositório de todos. Use git revert.

🚫
Commitar .env ou credentials

Bots varrem o GitHub em segundos. Configure .gitignore antes de qualquer commit.

🚫
git push --force na main

Sobrescreve commits dos colegas. Proteção de branch no GitHub previne isso.

🚫
Commits gigantes com "ajustes gerais"

Impossível de revisar, reverter ou entender. Use git add -p para commits granulares.
